## 2. 用户核心需求

- 数字人必须是“实时语音对话”体验，不是录一段、等十几秒再回复。
- 用户说完一句话后，理想情况下 3 秒内应该进入大模型回复流程。
- 语音识别必须边说边出文字，文字应尽快出现在聊天气泡里。
- 用户停顿约 1 秒，就认为本轮语音输入结束并自动发送。
- 默认进入页面后自动语音监听，不要每次都点语音按钮。
- 打开数字人页面后，数字人要说：“你好，请问有什么可以帮助你的呢？”
- 数字人说话时，不要被自己的外放声音打断。
- 只允许用户真人语音输入打断数字人的回复。
- 如果用户打断数字人，应该立即停止当前 TTS/回复，并识别用户新输入。
- 下方输入框不要残留已经发送的语音文字。
- 后续每次新增需求、现象、结论和修改，都必须同步写入本文档。

## 3. ASR 方案决策

用户明确要求切换到方案 C：

| 方案 | 架构 | 目标延迟 | 部署复杂度 | 成本 | 当前决策 |
| --- | --- | --- | --- | --- | --- |
| 当前 FunASR 独立服务 | 前端 -> 后端 -> FunASR | 1-2 秒或更慢 | 中 | 免费 | 不再作为主路径 |
| 方案 A 前端直连 FunASR | 前端 -> FunASR | 0.8-1.5 秒 | 低 | 免费 | 暂不做 |
| 方案 B 云 ASR API | 前端 -> 后端 -> 腾讯云 | 0.5-1 秒 | 低 | 约 0.02 元/分钟 | 暂不做 |
| 方案 C 浏览器内置 ASR | 前端 Web Speech API | 0.3-0.8 秒 | 极低 | 免费 | 作为默认主路径 |

当前目标：

- Chrome/Edge 上默认使用浏览器内置 `SpeechRecognition` / `webkitSpeechRecognition`。
- FunASR streaming 只作为浏览器不支持 Web Speech API 时的兜底。
- 不再默认依赖 FunASR `2pass final` 作为句子结束依据。

## 4. 已确认问题

### 4.1 HTTP 入口导致麦克风不稳定

浏览器对麦克风和语音能力要求安全上下文。HTTP 页面会导致权限、 websocket 和自动播放行为不稳定。

处理结论：

- `8880` 已切换为 HTTPS。
- 自签证书带 `IP Address:192.168.0.97` SAN。
- 第一次访问需要浏览器手动继续访问并允许麦克风。

### 4.2 慢主要不在 LLM/TTS

从 nginx 和后端日志看：

- `/adh/agent/v0/engine` 通常约 1.2-1.6 秒。
- `/adh/tts/v0/engine` 通常约 1.0-1.5 秒。
- 十几秒才反应的主要瓶颈在 ASR 链路，尤其是 FunASR final 或前端等待 final 的逻辑。

### 4.3 安静环境仍慢

用户已经把测试端电脑放到很安静的环境，仍然出现十几秒才响应。

结论：

- 不能继续简单归因于环境噪声。
- 必须更换主 ASR 路径为方案 C。

## 8. 2026-05-13 voice mode debug
- Symptom: voice button flips green/red while the page should stay in hands-free voice robot mode.
- Cause: button UI was tied to low-level `startMicRecord`. Browser Web Speech naturally ends and restarts recognition, so the UI flickered even though voice mode was still enabled.
- Fix: added `voiceModeActive`; the button now represents voice mode, not a single recognition instance. It stays active during Web Speech restart gaps and only turns off on explicit stop or microphone denial.
- Symptom: speech recognition sometimes became slow and looked like it fell back to the old slow path.
- Cause: `nativeStartTimeout` checked a stale React closure value of `startMicRecord`; even after Web Speech had started, the timeout could mis-detect startup failure after 1.5s.
- Fix: added `nativeRecognitionStartedRef`; startup timeout now checks actual `onstart`, and recovers native recognition instead of falling back to FunASR because of stale state.
- Symptom: text appears in the bubble, but agent reply does not come back.
- Cause: native Web Speech had competing submit paths in silence timer and `onend`, which could leave recognition state uncleared around `chat()`.
- Fix: native ASR now submits through `submitNativeSpeechTranscript()`, commits the human bubble, calls `chat(transcript, postProcess, false)`, clears the input text, resets native recognition state, and restarts listening. Added `[Voice] submit native transcript` console log to confirm the send entry is reached.

## 9. 2026-05-13 opening greeting not heard
- Symptom: backend logs show opening TTS generated successfully, but the page does not audibly say the greeting.
- Observed log: `/adh/tts/v0/engine` received `你好，请问有什么可以帮助你的呢？` and returned 200.
- Cause: automatic hands-free ASR starts around page load and can call playback-interrupt cleanup before or during the greeting. This can clear the queued greeting audio or prevent it from being heard.
- Fix: added `sentio:opening-greeting` state events from `chatbot/index.tsx`; `ChatInput` now treats opening greeting as active and delays automatic Web Speech startup until greeting playback finishes or a 7s fallback timeout expires. Manual voice button start can still interrupt playback.

## 10. 2026-05-13 current ASR path and no-response diagnosis
- Current main ASR path is Scheme C: browser built-in `SpeechRecognition` / `webkitSpeechRecognition`.
- In Scheme C, backend `/adh/asr` logs are expected to be absent. The first backend request after speech should be `/adh/agent/v0/engine`.
- Latest logs showed opening `/adh/tts` requests but no `/adh/agent`, so the no-response symptom is stuck before agent submission: browser ASR did not produce/submit text.
- Fix: explicitly request microphone permission with `navigator.mediaDevices.getUserMedia({ audio: true })` before starting Web Speech, show visible states (`Requesting microphone`, `Starting browser ASR`, `Listening`, `Microphone blocked`), and keep the primary path in browser ASR.

## 11. 2026-05-13 keep ASR as Scheme C only
- User clarified the issue is slowness and queued pipeline processing, not total no-response.
- Decision: do not silently fall back to FunASR streaming when Chrome/Edge supports Web Speech. Silent fallback can reintroduce `/adh/asr/v0/engine/stream` and make speech feel like slow serialized pipeline processing.
- Fix: `shouldUseRealtimeVoice()` now returns true only for browser Web Speech availability. Repeated native recovery no longer switches to streaming ASR. If browser ASR is unavailable, the UI shows `Browser ASR unavailable` instead of entering the old ASR pipeline.
- Optimization: microphone permission is requested once and cached with `micPermissionReadyRef`, avoiding repeated `getUserMedia` prompts/delays on every Web Speech restart.

## 12. 2026-05-14 realtime TTS playback
- User requirement: realtime voice assistant behavior, not slow queued one-by-one processing.
- Problem: `useChatWithAgent()` used `ttsRequestInFlight`, allowing only one TTS request at a time. Even when the agent streamed text, audio synthesis was serialized, so each ~1s TTS segment accumulated latency.
- Fix: changed TTS scheduling to first-chunk priority plus concurrent prefetch. Up to 3 TTS segments can synthesize in parallel; buffers are tagged with segment ids and flushed to Live2D in order, so audio order stays correct while later segments are prepared early.
- Additional latency reduction: before a full sentence punctuation arrives, the first chunk can be cut at 4+ chars, and later early chunks at 10-22 chars, allowing first audio to start sooner during streamed responses.

## 13. 2026-05-14 Live2D touch random voice interruption
- User requirement: random voice generated by clicking the digital human must not queue. A new click should interrupt the previous random voice and immediately play the newest one.
- Problem: touch voice used `Live2dManager.pushAudioQueue()` followed by `playAudio()`, so each click appended audio to the queue. Older TTS requests could also finish later and still enqueue stale audio.
- Fix: added `Live2dManager.playAudioNow(audioData)`, which stops current audio, clears the queue, pushes only the new audio, and starts playback.
- Fix: `chatbot/index.tsx` now keeps a touch voice request id and abort controller. A new touch aborts the previous touch TTS request, stops current audio immediately, and only the latest request is allowed to play when it returns.

## 14. 2026-05-14 voice utterance overwrite
- User requirement: voice input must not queue full utterances. A full utterance is defined as speech followed by more than 1s silence. If a new full utterance arrives while a previous agent/TTS response is still running, the new utterance must interrupt and replace the previous one.
- Problem: native Web Speech listening/restart was blocked while `chatting` or TTS playback was active, and `onresult` ignored results during TTS. That prevented user speech from interrupting the previous response.
- Fix: hands-free browser ASR now stays active during agent/TTS playback. `scheduleNativeRestart()` and auto restart no longer block on `chatting`/`ttsBlocked`. When Web Speech receives non-empty user text during playback, `clearPlaybackBlockForVoiceInput()` aborts the previous agent session, stops old TTS/audio, and the 1s silence submit sends only the latest utterance.

## 16. 2026-05-14 assistant echo filter
- User observed the digital human's own TTS text was recognized as user voice input.
- Cause: browser Web Speech listens through the microphone and can capture speaker audio. Keeping ASR active during TTS enables user interruption, but without echo filtering it also captures assistant speech.
- Fix: every assistant speech segment now dispatches `sentio:assistant-speech-text` before playback. This includes opening greeting, touch random voice, and agent TTS segments.
- Fix: `ChatInput` keeps recent assistant speech text and drops native ASR transcripts that are highly similar to those texts. Echo transcripts clear the draft bubble and are not submitted to the agent.
- This preserves interruption for real user speech while preventing the assistant from talking to itself.

## 17. 2026-05-14 echo filter false positive after TTS
- Symptom: after the digital human finishes speaking, real user speech can be ignored for several seconds, sometimes looking like ASR has no reaction.
- Cause: the first assistant echo filter was too broad: a 12s window plus loose Chinese character-overlap matching could treat normal short user replies as assistant echo because common characters overlap.
- Fix: tightened the assistant echo window to 5s, raised the similarity threshold to 0.84, and replaced loose overlap with LCS-based similarity.
- Fix: echo filtering now only applies to normalized texts with at least 4 characters, and direct substring filtering only applies when the user transcript has at least 6 characters.
- Expected behavior: the assistant's near-identical self-echo is still dropped, but different real user speech immediately after TTS should be allowed to interrupt and send `/adh/agent`.

## 18. 2026-05-14 unstable browser ASR restart
- Symptom: voice chat sometimes responds normally, then later stops reacting even though the user is speaking.
- Cause: browser Web Speech can naturally end or throw `no-speech`/`aborted`. Some restart guards still depended on React state values (`startMicRecord`, `startAsrConvert`) captured by older closures, so the app could believe ASR was busy when the real `SpeechRecognition` object had already ended.
- Fix: added synchronous refs for mic/ASR-busy state and changed the native restart scheduler, pending-restart effect, and 800ms watchdog to use `isNativeVoiceBusy()` instead of stale React state.
- Expected behavior: when Chrome/Edge Web Speech ends by itself, hands-free mode should pull it back up consistently instead of randomly staying silent.

## 19. 2026-05-14 short assistant echo leakage
- Symptom: the digital human can still recognize its own speech as user input, especially as short fragments like `你`, `好的`, or `可以`.
- Cause: the stricter echo filter intentionally ignored transcripts shorter than 4 normalized characters to avoid dropping real short user replies. Browser Web Speech often turns speaker audio into exactly these short fragments, so they leaked through during TTS playback.
- Fix: added a separate short-echo guard. During assistant playback and for 1.5s after playback state changes, transcripts up to 3 normalized characters are dropped if they appear inside recent assistant speech text.
- Expected behavior: short self-echo from the speaker is filtered, while normal short user replies outside the assistant playback window are still allowed.

## 20. 2026-05-14 opening greeting playback reliability
- Symptom: page load still sends the opening greeting TTS request, but the digital human sometimes does not audibly say `你好，请问有什么可以帮助你的呢？`.
- Observation: nginx access logs show `/adh/tts/v0/engine` shortly after `/sentio` page load, so the greeting synthesis request is not missing.
- Cause: greeting playback could run before Live2D/audio context is fully ready. The old flow pushed audio into the queue before `playAudio()`, so failed early attempts could leave stale queued audio or get cleared by other playback/ASR cleanup.
- Fix: added `Live2dManager.resumeAudioContext()` and changed the greeting flow to wait for `manager.isReady()`, retry up to 8 times, then play with `playAudioNow()` so there is only one latest greeting audio instead of repeated queue entries.
- Expected behavior: on fresh page load the greeting should play more reliably once the Live2D model and audio context are ready.

## 21. 2026-05-14 TTS generated but frontend playback can get stuck
- Symptom: user suspected the digital human/TTS stopped speaking.
- Verification: backend logs showed repeated `/adh/tts/v0/engine 200 OK` and `edgeTTS.py` inputs, so TTS synthesis itself was healthy.
- Cause: browser `AudioContext.resume()` can be blocked by autoplay policy when there is no user gesture. Awaiting it during greeting playback can stall the greeting flow, and starting a buffer while the context is still suspended can leave `_audioIsPlaying` true until the browser resumes audio.
- Fix: `resumeAudioContext()` now has a 600ms timeout, greeting playback no longer blocks on awaiting resume, and `playAudio()` releases the playback-blocked state if the audio context is still suspended after 1.2s.
- Expected behavior: if autoplay blocks sound, the app should not get stuck in a fake playing state; later user interaction or subsequent TTS can still play normally.

## 22. 2026-05-14 assistant speech interrupted by its own echo
- Symptom: the digital human often starts speaking but does not finish the sentence.
- Likely cause: while TTS is playing, browser Web Speech can hear the speaker output. The old `onresult` handler interrupted playback as soon as it saw any non-empty transcript during `ttsBlocked/chatting`, including interim or short assistant-echo fragments that were not caught by the echo filter.
- Fix: during assistant playback, native browser ASR no longer calls `clearPlaybackBlockForVoiceInput()` for interim results or short transcripts. Barge-in is allowed only for final transcripts with at least 4 normalized characters and not matching assistant echo.
- Fix: ignored playback-period fragments clear the temporary transcript/draft so they cannot accumulate and submit later.
- Expected behavior: the assistant should finish its own TTS more reliably, while real user interruption still works for clear final speech.

## 23. 2026-05-14 prioritize complete TTS over playback-period barge-in
- Symptom: screenshots showed multiple user bubbles that looked like assistant/self-audio fragments, followed by assistant replies, meaning playback-period ASR still submitted false user input.
- Cause: even with stricter final/length rules, browser ASR can produce final-looking transcripts from speaker output or room noise. Allowing any playback-period transcript to interrupt is too fragile without acoustic echo cancellation.
- Fix: while `ttsBlocked` or `chatting` is true, native browser ASR now ignores all transcripts, clears draft text, and does not submit/interrupt. Listening resumes after playback/reply state clears.
- Tradeoff: users cannot reliably interrupt during the assistant's own TTS in this version; the priority is that the assistant finishes speaking and does not talk to itself.
